# Architecture fit: ADK Workflow or Pydantic AI under our own loop

Judged on design alone, with migration cost set aside. Sources: `use-cases.md`, the two architecture reports, the two footprint reports, and the framework source at google-adk v2.13.0 and pydantic-ai v2.64.0.

## Verdict

Pydantic AI agents under a turn loop we own fit the harness better than ADK's `Workflow`. Add a durable engine only for work that leaves the user's stream. Keep the interactive turn out of the engine.

Four architectures were compared:

1. ADK `Workflow` as the orchestration and agent runtime, as today.
1. Our own turn loop: a persisted cursor, one stored `Conversation` per agent, and plan, approval and turn records in our Postgres ledger under the compare-and-swap lease we already run.
1. Architecture 2 with the whole turn inside a durable engine (DBOS, Temporal, Restate or pgtask).
1. Architecture 2 with an engine or Postgres task queue for detached work only: turns that outlive the client, polling of background mints, manifest replay, compaction, a reply judge. This is the recommendation.

## The properties that decide it

First, where a pause lives and how resume finds it. ADK records a pause as an `adk_request_input` call in the session log, and a resume reruns the root from START, fast-forwarding nodes that have recorded outcomes (`workflow/utils/_replay_interceptor.py`). That is exact only when the code is unchanged and deterministic between pause and resume. Our pauses are few, named, last minutes to days, and span deploys. A stored cursor with the plan revision, interrupt id and per-agent history is a lookup, correct by construction. Engines replay too: DBOS raises `DBOSUnexpectedStepError` when step order changes across a deploy, and pgtask reruns renamed steps. Architecture 3 therefore brings back the defect class behind `_turn_ran_before`. That is why the engine belongs on detached work measured in minutes, and not on approval pauses measured in days.

Second, who owns model context. ADK's `_is_event_belongs_to_branch` returns true when either branch is empty (`flows/llm_flows/context/_contents.py:776`), so the default is to show. Every new node, agent and parallel worker adds stamping and a leak test. Pydantic AI gives each agent its own message list and one hook where the request is assembled. The product rests on models seeing digests in curated views (demand 2), so the default matters more as agents, skills and capability cards grow.

Third, whether a pause is a value or an exception. In ADK a child's interrupt becomes `NodeInterruptedError`, a `BaseException`, raised through the awaiting node (`workflow/_dynamic_node_scheduler.py:845-847`). The `run_node` docstring forbids wrapping the call in a task (`agents/context.py:453-456`). Streaming from planning (E) and parallel pausable work (F) both need a producer task under a consumer, which this design rules out. In Pydantic AI a pause ends the run with `DeferredToolRequests` as its output. The orchestrator's `plan` tool becomes a deferred call that our loop resolves by running the planner and the approval gate, which is the current graph's routing written as code.

## The strongest argument against

Under architecture 2 or 4 we own the orchestration runtime for good: cursor, lease, checkpoints, cancel and crash handling. Pydantic AI's churn would sit under our durable records, at about three releases a week, with Harness on 0.x and message history carrying no schema version. Google, meanwhile, is investing in `Workflow` and a managed runtime that may close the gaps (steering RFC #7642, streaming lifecycle RFC #7455).

It does not hold for the runtime. We already own the lease, checkpoint, cross-instance cancel and frame translator on ADK, in about 700 lines of `studio_state.py` built on a session service bent into a compare-and-swap store. What ADK adds on top is replay, the source of the defects. No primary source shows the managed runtime fixing liveness or replay cost.

It does hold for churn. Treat our records as canonical: plan, approvals, digests and turn records. Keep each agent's `Conversation` as derived state that can be rebuilt or dropped, pin the version, and run a replay test on stored histories with every upgrade. If that discipline proves too costly, the fallback is the same loop on plain `google-genai`, which keeps every property above except N.

## What the evidence could not establish

- Live progress from inside planning. No one has run a planner whose `propose_plan` tool emits translator progress through `ctx.emit` while our loop streams and a pause arrives. Prototype on scripted `FunctionModel` runs: pass if the first progress frame reaches the client within 2 s of planner start, and a pause mid-planning loses no emitted event and resumes in a fresh process to the same plan as an unpaused run.
- Pydantic AI on our Gemini declaration. `VALIDATED` calling on a `propose_plan`-sized schema, thought-signature round trips and `PrefixCache` re-hosting are untested. Pass lines as in `consult-verdict.md`: same declaration bytes as `compact_schema`, cached share within 5 points, p50 first chunk within 10%.
- A deferred `plan` call across processes. Pause the orchestrator on `plan`, run the planner, pause again for approval, kill the process, then resume both runs elsewhere. Pass if the orchestrator's final history equals an unpaused scripted run's, byte for byte, excluding timestamps.
- History stability across upgrades. Pass if a corpus of 200 `Conversation` records stored under 2.64.0 loads and replays under each release over a four-week window with zero decode failures.
- Whether turns must outlive their stream. Today a disconnect cancels the run. Measure on deployed dev the share of turns over 60 s (the ChatGPT cap) or ending in client disconnect. Over 5% makes the detached half of architecture 4 required now; under that, defer it. Detached work needs CPU after the stream ends. The `ai` service runs `cpu_idle = true`, so it needs a separate worker service or that setting priced.
- ADK's direction. Source cannot show whether Google will ship queued steering, live node streaming or snapshot resume (#7642, #7455). None changes the verdict unless the branch default also flips.

## Decisions for the user

1. Engine scope. Options: detached work only (recommended), whole turn, or none. Detached work only gives crash-safe background jobs and start-and-poll handles for outside clients, and keeps live streaming and deploy-safe pauses. Whole turn adds crash recovery mid-planning but costs live streaming and adds replay-version rules. None is the cheapest choice and leaves J to our own queue.
1. Should a planned turn outlive the client stream, running detached with the stream as a subscriber? Recommended yes, given a 659 s worst turn against a 100 s Cloudflare cut and a 60 s ChatGPT cap. Strongest objection: cancel semantics change, since a closed tab no longer stops work, so Stop must become explicit. That holds as a cost, not as a reason to refuse.
1. The agent layer under the loop: Pydantic AI (recommended) or plain `google-genai`. Pydantic AI supplies validation, `FunctionModel` fakes, streaming events and provider breadth. `google-genai` avoids the churn and loses N. Choose Pydantic AI unless the history-stability test above fails.
