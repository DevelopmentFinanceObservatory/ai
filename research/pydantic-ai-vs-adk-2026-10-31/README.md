# Pydantic AI or Google ADK: which architecture fits the harness

Judged on design alone, against google-adk 2.13.0 and pydantic-ai 2.64.0 as of 2026-10-31; the planner prototypes were rerun on pydantic-ai 2.66.0 against dev at 245c0a44. The cost of moving is in `effort-and-cost.md`.

## Recommendation

On architecture, Pydantic AI agents under a turn loop we own fit the harness better than ADK's `Workflow`. Add a durable engine (DBOS, Temporal or a Postgres task queue) only for work that leaves the user's stream: long mints, turns that outlive the client, replay of shared cards. Keep the interactive turn out of the engine.

The choice is really two decisions stacked. The first is who owns the turn: ADK's replay engine or an explicit state machine of ours. Most of the gain comes from owning the turn. The second is which agent loop runs under it: Pydantic AI or ADK's `LlmAgent`. Pydantic AI wins there on context control, typing, streaming, tool search and model breadth. It leaves the turn to us, so the two decisions go together.

The turn needs no graph library. `harness/graph/workflow.py` wires ten nodes with five edges that loop back (`ask` and `plan_done` to `orchestrate`, `approve` and `execute` to `planner`, `switch` to `approve`), three user pauses (`ask`, the planner's own ask and `approve`) and no fan-out between nodes; the only parallel work runs inside `execute`. An enum of states, one async function per state and a loop that dispatches on the stored state express that directly, and resume becomes a ledger read followed by one call. A graph library would pay for itself only if separate agents ran in parallel and each could pause on its own, such as one approval per variant in a comparative plan. Nothing committed asks for that, and `asyncio.gather` inside one state covers the common case. So `pydantic_graph` dropping persistence in V2, because snapshots of parallel steps cannot be made consistent, costs us nothing.

## What the harness has to do

The product rests on three demands, drawn from 16 built and planned capabilities (`use-cases.md`):

1. Durable human pauses. Approval, amendment, clarification and cancel all pause a turn that resumes on another instance, sometimes days and several deploys later, with the approved plan's bytes intact.
1. Context control. Models see digests while rows stay out of band. Each agent gets a curated view, long conversations need compaction and recall, and a catalogue of skills and capabilities keeps growing.
1. Live streaming. The wire contract is frozen, progress must stream from inside long steps such as planning (median 59 s, worst 659 s), and the same components serve the site and MCP Apps hosts.

Next come parallel work inside a turn, background data work that outlives a request, outside agents calling the workflow through MCP, and possibly a second model provider.

## How each framework works

ADK is an append-only session event log with a graph scheduler on top. Every durable fact is an event row; a model's prompt is assembled from that shared log by filter rules; a pause is a function call in the log; and resume reruns the workflow from START, fast-forwarding nodes that have a recorded outcome. One mechanism serves history, state, resume and tracing (`architecture-adk.md`).

Pydantic AI is a stateless agent loop with typed hooks. A run takes a message history and typed dependencies and returns messages. Nothing persists unless we store it. A pause for a human ends the run with the pending tool calls as its output; a later run on any instance picks up from the stored `Conversation`. Every model request passes one hook where the developer can rewrite messages, tools, instructions and model (`architecture-pydantic-ai.md`).

## The three properties that decide it

Where a pause lives. ADK's replay is exact only when the code between pause and resume is unchanged and deterministic. Our pauses span deploys, so a node added in a release runs live in the middle of a resumed turn; that is why `seed` carries `_turn_ran_before`, and every new node needs the same guard. A stored cursor holding the plan revision, the interrupt id and each agent's history is a lookup, correct by construction. Durable engines replay too (DBOS raises `DBOSUnexpectedStepError` when step order changes across a deploy), which is why they suit minutes-long background work and not approval pauses that last days.

Who owns model context. In ADK an event with no branch reaches every agent (`_contents.py:776`), so isolation is opt-in, stamped per event and checked by tests. A plan of over 100,000 characters once reached prompts this way. In Pydantic AI each agent owns its message list, and one hook assembles each request. Since the product depends on curated views, the default matters more with every agent, skill and capability added.

Whether a pause is a value or an exception. In ADK a child agent's pause raises `NodeInterruptedError`, a `BaseException`, up through the parent node, and `run_node` must be awaited directly and never wrapped in a task (`agents/context.py:453-456`). That rules out a producer task under a streaming consumer for any agent that pauses from inside `ctx.run_node`, which parallel pausable work needs. In Pydantic AI a pause is the run's return value, so an agent can run in a task while the loop streams. Of the three properties this one weighs least for the planner on dev today: its ask is a plain tool, the `planner` node pauses after the run ends (`harness/graph/planning.py`), and a pick's replan already runs the planner in a task. Dev already shows planner progress live: ADK streams the planner agent's own events while it runs and `studio_translate.py` draws its status lines from them. The node queues only the seam's own reports, which repeat what those events carry.

## Capability by capability

| Capability                          | ADK `Workflow`                                                              | Pydantic AI under our loop                                              |
| ----------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Durable human pauses                | Native, but replay hazards across deploys                                   | A cursor and stored records; deploy-safe                                |
| Per-agent context                   | Shared log, shown by default                                                | Separate histories, one request hook                                    |
| Live streaming to the UI            | About 900 lines translate node paths and branches into frames               | The loop emits our frames; `ctx.emit` from tools                        |
| Progress from inside planning       | Live: ADK streams the planner's events and the translator draws status      | A pause is a value; planner runs in a task                              |
| Steering a running turn             | No text-mode API; cancel is in-process                                      | `enqueue` injects at the next request; cross-instance signal is ours    |
| Parallel agents                     | Sub-branches; state deltas merge by dict key                                | `asyncio.gather` over separate runs, with concurrency limits            |
| Direct execution beside the planner | Shared services travel as state keys and closures                           | One typed `deps` object shared by both agents                           |
| Long conversations                  | Compaction appends summaries; rows never pruned; resume reads the whole log | History processors replace history; recall reads our records            |
| Growing tool catalogue              | No tool search; a changing tool list drops the cache                        | `ToolSearch` with deferred loading                                      |
| Background data work                | No worker; work dies with the stream                                        | Not provided; an engine or queue does it (the recommended add-on)       |
| Outside agents through MCP          | Agent-as-MCP and A2A experimental                                           | A turn is a function a FastMCP tool can call; A2A is a separate package |
| Second model provider               | Gemini-first; LiteLLM and Anthropic adapters under repair                   | About two dozen providers, per-step model choice                        |
| Gemini-specific depth               | Wide and early                                                              | Wide; explicit caching stays ours on either                             |

Neither framework gives cross-instance coordination. We already run our own lease, checkpoint and cancel on a session table, and that stays.

## Where ADK is stronger

ADK's single log is a smaller idea than ours would be: one append gives history, state, resume and traces, and pause and resume across processes work today with no code of ours. Google's investment is heavy and aimed at `Workflow`, with a managed runtime behind it, and Gemini features arrive there early. If Google ships queued steering (RFC #7642), live observation of a running agent's events (#7094) and a branch default that hides rather than shows, the case above narrows. None of those is committed: the steering RFC is from an outside contributor and its implementing PR (#7643) was closed unmerged, and no source shows a change to the branch default or to replay. ADK 2.14.0 fixed several resume defects, among them a finished node rerunning when a later interrupt resumes.

## The strongest argument against the recommendation

Owning the turn loop means owning a runtime for good, and Pydantic AI changes fast underneath it: about three releases a week, its harness package still 0.x, and stored message history with no schema version. The runtime half of this objection is weak, because we already own the lease, checkpoint, cancel and frame translation on ADK; replay is what ADK adds on top, and replay causes the defects. The churn half holds. The answer is to keep our own records (plans, approvals, digests, turn records) canonical, treat each agent's `Conversation` as derived state we can rebuild, pin the version, and replay stored histories on every upgrade. So far the format has held: records from ten releases load and resume under every later one. If that discipline fails, the same loop runs on plain `google-genai` and keeps every property above except provider breadth.

## What the prototype showed

A planner prototype tested each claim above (`prototype-results.md`). Every pass line held, with one condition: the planner must keep Gemini's function calling in `AUTO` mode, as ADK does, and not in `VALIDATED`, Pydantic AI's default.

- Live progress and pauses. Under our own loop, a progress event from inside `propose_plan` reached the client within 2 s while the tool was still running, and a pause mid-planning lost no event.
- Surviving a kill. A turn paused for approval, its process killed with SIGKILL, finished in a fresh process with orchestrator and planner histories identical to an unpaused run once timestamps and run ids were normalised.
- Deploy-safe resume. A step added to the start of a turn did not run when an older paused turn resumed, and two concurrent resumes of one pause let exactly one through.
- Stored histories. A paused `Conversation` written by each release from 2.55.0 to 2.64.0 loads and resumes under every later release, and under every earlier one. Releases only added fields. That holds for the record shapes tested; tool retries (2.60), compaction parts and tool-availability deltas (2.62) are stored in shapes older releases cannot read, so rollback past those releases is one-way for histories that hold them.
- The planner on Gemini. Over 558 paired entries on the 62 `planner_entry` tasks, the Pydantic AI planner in `AUTO` mode accepted 127 of 177 first proposals against ADK's 129, kept the cached share at 85.3% against 84.7%, ran first chunks at 1.04 times ADK's p50, and lost no thought signature. The `propose_plan` declaration reached Gemini byte for byte as ADK sends it. `VALIDATED` mode slowed the first chunk by 20% and each entry by 3 s, and one refusal task stopped ending as it should.

Two reviews of Pydantic AI's docs and of production reports, together with dev's upgrade to ADK 2.13, shrink four costs and add four risks (`patterns-and-risks.md`). Pydantic AI already answers an unknown tool with the tool list and re-prompts an empty response. A cache prefix built from the canonical declarations should let both frameworks share one Gemini cache. Public hooks replace the prototype's patch of the google-genai client. The new risks each need a rule in the loop: an effect ledger, because a pause resumes at least once; no `enqueue` where a turn can pause; an envelope with a schema version around each stored history; and a fresh usage counter per turn. ADK 2.13 showed the same kind of wire drift on its side: a line it appends to the instruction took the orchestrator's first call from 0 to as many as 703 reasoning tokens.

A second prototype put a Pydantic AI planner inside ADK's own `planner` workflow node (`prototype-node-stream.md`). It streamed progress live: the first frame reached Studio's SSE client in 0.09 to 0.20 s while `propose_plan` was still running, against about 3.1 s, after planning, for dev's node. It also lost no frame when the planner asked the user, resumed from the stored history after the answer, survived SIGKILL, stopped cleanly and kept the turn's stored records equal to dev's. So the planner can move first, inside the ADK turn, and unblock live planning progress before the turn loop changes. ADK accepted the same answer twice after a kill, so a production node needs its own duplicate guard. A third stage ran each planner segment as a DBOS workflow inside the node, so a kill repeats no model call. Taking over a segment from a dead instance, and keeping its progress on the instance the client is connected to, would need work of our own (`prototype-node-stream/dbos/NOTES.md`).

Three more prototypes tested the rest of the harness (`prototype-harness.md`). The orchestrator ran on Pydantic AI inside ADK's `orchestrate` node, with frames and records equal to dev's, so both agents can move while ADK keeps the workflow; a cut mid-stream by the turn budget is the one behaviour that did not carry over. A turn loop of our own, a cursor row in Postgres with compare-and-swap writes, passed five failure cases with no guard per node. On the same cases ADK without dev's guards ran a newly deployed node mid-turn and finished a crashed turn with three steps missing and no error, and with the guards left that turn with nothing to continue it. `execute` on DBOS survived a disconnect and a kill, but only on the test ledger: Studio's ledger refuses the run's writes once the stream ends, so each run needs its own lease.

The planner's code also works as MCP tools an outside model drives, with the client paying for every model call (`prototype-plan-tools/`, results in `prototype-plan-tools/live/clients.md`). On the second version of the tools, Gemini 3.8 Flash, gpt-6-luna, Claude Sonnet and Claude Haiku each landed and ran an accepted plan in every conversation on ten tasks against dev data, 60 of 60, against 29 of 30 entries for our planner. Leaving out one task whose reference is out of date, their plans were right in 15 of 18 (Gemini with elicitation), 7 of 9, 9 of 9 and 7 of 9 conversations, against 24 of 27. `start_plan` takes the client's searches, `run_plan` returns the rows, and with MCP elicitation every approval came from the user and none from the model. A client conversation costs Gemini about 508,000 input tokens, 87% from cache, because every request carries the `propose_plan` schema and the planner's guidance.

Whether our own planner should reach that code over MCP turns on whether plan-mcp is served to outside clients (`prototype-plan-tools/harness-ab/NOTES.md`). Over MCP, the planner's tools cost no more: the transport adds 3 to 7 ms to an entry of 10 to 14 s in process and 16 to 38 ms over loopback HTTP, and each request is 410 to 1,053 tokens smaller. Neither result comes from MCP. The saving is the lean `propose_plan` declaration and the shorter ask tool, which the in-process planner can take as they are, and the move removes no harness code: plan-mcp imports the planner's tools, its seam and the `execute` node, and the harness would add about 200 lines to reach it. It would also break four things that work today: Studio's pause and resume under `adk_request_input`, the graph's own copy of the plan that approval, `execute` and `revise` read, the turn's time limit across a proposal, and one store for a turn's state. Served on `/mcp`, plan-mcp would offer outside clients the code our harness runs, so the harness and the public tools share one planner either way. If plan-mcp is served, moving the harness onto it keeps one path to the planner; that needs a `revise` tool, the turn's deadline passed in, and Studio's pause answering `record_user_answer`. If it is not served, the move buys nothing. Dev's planner ask now pauses at the node, so the first of the four breaks is smaller than measured here.

On Pydantic AI the planner reaches plan-mcp with stock parts (`prototype-plan-tools/harness-pai/NOTES.md`): an `MCPToolset`, a prepared view that hides `plan_session` and declares the ask as a deferred tool, and a `process_tool_call` hook, in 79 lines. Offline, the model is offered and reads the same declarations and answers as the ADK planner over MCP, character for character, and the ask pauses, survives a serialised history and resumes with the answer recorded `by: harness`, landing the same plan. MCP adds 0.9 ms per call in process and 4.6 ms over loopback HTTP. A server fault reaches the model as a retry that uses the tool's retry budget, so a production client sets `tool_error_behavior="failed"`.

The real planner then ran on Pydantic AI inside the `planner` node of the real Studio turn, against current dev (`prototype-planner-live/RESULTS.md`). Its tool bodies first moved onto the neutral `PlannerCall` with thin ADK wrappers, a change of 271 lines added and 1,620 removed that keeps every declaration byte-equal (`s0.diff`). Offline, across all 70 `planner_entry` tasks, every case ends as it does on ADK and all 230 requests match apart from six pinned wire differences. Inside the Studio turn, frames, requests and stored records equal dev's for a planned turn, an ask and its resume, an amendment, a refusal replan, a pick's replan and Stop. On Postgres, rows, bytes, a resume from a fresh process, a kill mid-planning and a second turn all match dev's node. On live Gemini over 840 paired entries, first proposals accepted differ by +2.4 points (-2.9 to +7.9), the cached share by +0.1 points, and time outside model calls is 0.02 s against 0.06 s; median planner time is 6.9% higher with an interval from -13.5% to +32.8%, so slower planning is not ruled out. Planner time on both arms is driven by model calls that reason for 2,000 tokens or more, in about a third of entries, which the descriptions of the planner's skill tools trigger. Forty live Studio turns with approval and `execute` all ran to the end. Six behaviours differed from dev and were closed with tests: a tool running after a budget cut, error endings, resume across the two planners, state writes lost on Stop, tracing spans, and a retry on an empty response. The design that came out keeps `PlannerSeam.__call__`, runs the Pydantic AI loop as a function node that writes the same planner events ADK does, and keeps the session's events as the one stored record, so a turn can pause under one planner and resume under the other. `RESULTS.md` lists eight production slices, the first five of which ship on ADK alone.

Turns do need to outlive the client. On production from 5 October to 10 November, 26% of 2,203 turns ran past 60 s of working time and 11% past 100 s, and a planned turn's approval wait is 197 s at the 90th percentile.

Still open: `revise` through the `switch` node, the Cloud SQL connector path, the long-reasoning share on each arm once the planner's skill tool carries a short description, and the orchestrator on live Gemini. Most defects users meet are outside the framework question: 23 of the last 60 merged fixes correct how a plan binds sources or does arithmetic.

## Decisions for you

1. Whether to adopt the architecture: an owned turn loop with Pydantic AI agents in `AUTO` function-calling mode. The prototypes passed every line; the first step is the planner, ported in the slices `prototype-planner-live/RESULTS.md` lists, behind a flag inside the ADK turn.
1. Engine scope: detached work only (recommended), the whole turn (crash recovery mid-planning, at the cost of live streaming), or none.
1. Whether a planned turn should keep running after the client disconnects, with the stream as a subscriber. Recommended, given that 11% of production turns run past 100 s of working time, a 659 s worst turn, Cloudflare's 100 s cut and ChatGPT's 60 s cap; Stop then becomes an explicit action.
