# Plan-and-run MCP tools for outside models

The planner's code runs without its model behind four MCP tools, and an outside model can drive it. This is the second version, built to close the gaps four live clients hit (`live/clients.md`). All 151 tests pass in 27 s, twice in a row. Every reference plan of the 70 planner-entry tasks still lands as dev's planner entry records it, and 21 refused drafts still answer as dev's planner answers them, in the words `outward.py` gives an outside model. An outside model now reads 58,452 characters before its first proposal, against 63,556 from the first version and 61,523 for DFO's planner today.

## Design

The server is `FastMCP("plan-mcp")` (`server.py`) over `PlanningService` (`plan_tools.py`). It imports harness code and changes none.

- `start_plan(brief, asks, spec_ids, searches)` opens a plan session. `spec_ids` are the ids the client's own public `search` calls returned. Each is read as `get_data` reads a bare id: its identity from data-mcp's definition store, else dfo-apis' registry (`serve.held_identity`), which must hash to the id (`data_mcp.definition_writes.caller_definition`). Search is then asked that identity again through data-mcp's `resolve_definition` and must answer it as the one dataset the id names (`translator.discovery.resolved_spec`), as the graph's `seed` node takes a dataset a Studio user brought from Search. The part is stored as `search` stores one (`store_search`, origin `seed`), so it becomes a pin source. `searches`, the first version's path, still runs each search again through the orchestrator's own `search` tool, and a client may send neither. The rest is as before: the orchestrator's `plan` tool, the graph's `route` and `plan_start` nodes, and `PlannerSeam.__call__` stopped where it would call the model.
- `propose_plan` is the served planner's own tool object, called through ADK's `FunctionTool.run_async` on a tool context over the session's state and events. Its answer passes through `outward.outward`. An accepted answer gains `card`.
- `record_user_answer` asks the user what a refusal leaves to them. A client that declares MCP elicitation has plan-mcp ask the user itself, and the model's `answer` is not read. Any other client sends the user's reply as `answer`. Each answer is recorded `by` the user or the client.
- `run_plan(plan_session, version, approved, wait_s)` runs a version once it was declared ready, while it is the plan on record, and once the user's approval is on record: asked through elicitation, with the card as the message, or, without it, `approved: true` on the client's word. A finished run answers dev's hand-back, `approved_by`, and `data`: per frame its id, the `{spec_id, content_version}` pair the public tools read, and its rows (`outward.table`) while all frames' rows stay within 60 rows and 6,000 characters, else its row count. `plan_tools.ROW_CAP` gives the reasoning: the live runs' handed-back frames held at most 16 rows but one, and 6,000 characters is under 4% of one Gemini client request.

Elicitation uses MCP 2026-07-28 input requests (`InputRequiredResult`), which a FastMCP client drives through its elicitation handler and then repeats the call with the reply. A handshake-era connection is asked through `ctx.elicit`. FastMCP 4 refuses `ctx.elicit` on a 2026-07-28 connection, so both are needed.

Every tool reads its arguments with `outward.drop_unset` against its full schema, is listed with the lean schema (`outward.lean`), carries `strict: false` in its `_meta`, and is registered at FastMCP version 2. Sessions live in `PlanningService.sessions` and are saved to a `SessionStore` after every change: `store.SqliteSessions` when served. They are keyed on `"ps_" + token_urlsafe(16)` and bound to the caller in `x-dfo-caller`.

## P5: what an outside model reads before its first proposal

Characters as compact JSON for schemas. `measurements.json` holds the full numbers.

| Read                                  | First version               | Second version              |
| ------------------------------------- | --------------------------- | --------------------------- |
| `propose_plan` declaration            | 35,167                      | 32,210                      |
| `start_plan` declaration              | 3,598                       | 2,342                       |
| `record_user_answer` declaration      | 1,419                       | 941                         |
| `run_plan` declaration                | 788                         | 744                         |
| Guidance                              | 20,829                      | 20,460                      |
| Planner's first message, median of 70 | 1,755                       | 1,755                       |
| Total                                 | 63,556, about 15,900 tokens | 58,452, about 14,600 tokens |

The declarations drop the bounds and flags the planner validates anyway (`additionalProperties`, `minLength`, `maxLength`, `minimum`, `maximum`, `maxItems`, `default`), 3,556 characters of `propose_plan`'s 35,515; a refusal's `expected` names them where a value breaks one. The id `pattern`s and every description stay. `start_plan` lost the orchestrator `plan` tool's 1,300-character description, and the guidance's preamble went from 691 characters to 319, because refusals and the guidance now name `record_user_answer` themselves. DFO's planner reads 61,523 today. All four declarations pass both vendors' non-strict rules; strict mode would still reject them, which is why each says `strict: false`.

The guidance is served three ways, and `start_plan`'s answer is the one every client reads. The brief offered an MCP prompt, a resource, or a skill through `get_skill`. A prompt is something a user invokes, not something a model reads. A resource reaches the model only where the host lets it read one: Claude Code can, Pydantic AI's `MCPToolset` lists no resources, and neither does the `dfo` CLI, so two of the four live clients would plan without it. A skill means a `get_skill` entry, which lives in DFO's skills store and reaches dfo-apis through the dfo-pipelines publish, outside these directories. So the guidance stays in `start_plan`'s answer, read once per session when it is needed, and is also the resource `plan-mcp://guidance` and the prompt `plan_guidance` for hosts that read those. `PlanMcp(guidance_in_answer=False)` leaves it out of the answer for a client that already holds the planner's instruction, such as the harness's own planner.

## The "constant 2015 US dollars" card

In `claude-haiku-series-gdp-ghana-v2`, the card's summary and step said "Gross domestic product at constant prices of 2015 in US dollars" for UNIDO's `NA_GDPCOD`, whose unit node `undata/UNIT_MEASURE-CR_USD_K` states constant prices and no base year. The words are the source's own measure label and Search's sentence: `plan_display._counted` takes `source.measure_label` (`services/harness/src/harness/plan_display.py:573`) and `card_rows` takes `source.sentence` (`:311`). The compiler reads the unit by its structure and refuses to trust a base year that only a label states (`services/harness/src/compiler/evidence.py:1797-1801`), which is why the plan asking for 2015 prices was referred `requirement_unmeetable` and the landed plan states no base year. Dev runs this code for every Studio card today. plan-mcp's `card` is `plan_display`'s output, so the defect reaches it, but the fix belongs in `plan_display`: read the unit as `compiler.evidence._structured_reading` does and say "base year not stated" where the label and the unit disagree. Patching the words in plan-mcp would mean matching years in label text, so plan-mcp leaves the card as dev shows it. The graph's UNIDO unit node lacking its base year is the data-side cause.

## Refusal codes for dfo-spec-kit

plan-mcp writes these codes of its own, each in the planner's refusal shape: `plan_session_unknown`, `search_failed`, `hand_off_refused`, `plan_version_not_ready`, `plan_version_superseded`, `run_failed`, `spec_not_held`, `spec_not_resolved` and `plan_not_approved`. It also answers the outcome `referred`, whose code is the translator's referral kind, and reuses the planner's `invalid_arguments`, with `expected` naming each missing argument's schema, for a call to `start_plan`, `record_user_answer` or `run_plan` that leaves out a required argument (`test_i5_schema.py`).

## Versioning

Every tool is registered at FastMCP version 2 (`server.TOOLS_VERSION`). A later schema registers its own tool classes at version 3 on the same server under the same names. A listing then shows version 3 with `_meta.fastmcp.versions: ["3", "2"]`, and a client that pins version 2 in `_meta.fastmcp.version` keeps calling this one (`test_i7_a_later_version_lives_beside_this_one`). Sessions carry no version, so a session opened through version 2 can be carried on by version 3 only if version 3 reads the same session document.

## What only a change in `services/` could fix

- The public `search` refuses a strict client's empty values: `dcid: ""` breaks `min_length=1` (`services/data-mcp/src/data_mcp/search_tool.py:129`) and `target_year: 0` breaks `ge=1000` (`:168`). The same rule belongs in the combined server's argument middleware, `_PublicArguments.on_call_tool` (`services/harness/src/harness/combined_mcp.py:970`), which sees every public call with the tool's listed schema before the child validates it.
- The guidance as a `get_skill` skill: a skills-store entry published through dfo-pipelines.
- The card's base year: `plan_display` reading the structured unit, above.
- Mounting plan-mcp on the public `/mcp`, under its middleware (budgets, rate limits, request logs, refusal shapes), about 30 lines in `harness/combined_mcp.py`.
- Registering the codes above in dfo-spec-kit's `codes.json`.
- The planner's own instruction and refusals naming `record_user_answer`: plan-mcp renames `adk_request_input` on the way out (`outward.guidance_text`, `outward.outward`).

## What this relies on

- Harness, private: `PlannerSeam._propose` (overridden) and `PlannerSeam._agent`'s tools and instruction; ADK's `FunctionTool._get_declaration`; `harness.orchestrator_tools._frame_work` (`serve.frame_rows`); `harness.scripted_plan`'s `_scripted_source`, `_SCRIPTED_CAPABILITIES`, `_SCHEMAS_BY_NAME` and step ids (P3 only); `entry._no_anchor_read` and `presentation_mcp.client._frame_ref_or_refusal` (tests only).
- Harness, public: `translator.discovery.resolve_definition`, `resolved_spec`, `resolving_once`; `harness.seeds.stale_reason`; `harness.graph.state.store_search` and `frame_store_ref`; `data_mcp.definition_writes.caller_definition`; data-mcp's definition store and upstream client, and dfo-apis' `GET /api/datasets/{id}/options` (live only).
- Harness, duck-typed: as in the first version, the planner's tools, the translator and `declare_ready` read a tool context's `state`, `session.events`, `session.id`, `actions`, `function_call_id` and `tool_confirmation`. The ask tool reads its arguments alone, so `check_ask` runs it before the user is asked.
- FastMCP 4.0.10: `Tool` subclasses with their own `parameters`, `meta` and `version`; `InputRequiredToolResult`, `Context.input_responses`, `Context._is_modern_protocol` (private), `Context.elicit`, `parse_elicit_response_type` and `handle_elicit_accept`; component versions and `dedupe_with_versions`.
- ADK: `FunctionTool.run_async`, `Event`, a `Runner` over a two-node `Workflow`, `Event.actions.route`, and `InMemorySessionService.get_session` for the run's registered frames.

## What a production version would change

- Sessions in Postgres beside the Studio ledger, keyed on the returned id and the caller, about 80 lines over `store.py`'s document; an advisory lock per session so two instances cannot write one session at once.
- Durable runs, about 100 lines: a run that outlives the instance and is found again by session and version, as `prototype-background-execute/` does. A restart now loses an in-flight run, which runs again on the next `run_plan`.
- The guidance as a skill and the card's base year, above.
- A cap on reruns of `start_plan` and on `spec_ids` per session: each spec_id costs a registry read and a Search resubmit.
- Reads that need no shared bucket: `frame_rows` reads `spec_` frames from the materialisation store, and `start_plan` reads a spec_id no `get_data` has registered from data-mcp's definition store. A separate plan-mcp process shares them only when `FRAME_STORE_BUCKET` and `DEFINITION_STORE_BUCKET` are set (`serve.install_shared_stores`); derived frames are read from dfo-apis either way. Mounted on `/mcp`, plan-mcp shares the harness's stores.

## Not covered

- Plans that read real data offline: P3, I2 and I4 run the scripted plan; I2's rows come from a stub reader, so `frame_rows` itself is exercised only live.
- `get_data` with a run's pair: it takes a fetched frame's `spec_id`, and the scripted run hands back a derived frame, so I2 checks `export_data` and `describe_frame` only.
- Referral asks with `candidates` through elicitation, and a free-text elicitation; prices asks; plan-card switches.
- Several instances sharing one SQLite file, and an elicitation the client never answers.
- Live client models: the rig is ready for the rerun (`live/NOTES.md`).
