# harness

`harness` runs the agent powering DFO Studio's chat-and-canvas workspace. The service wraps Google Agent Development Kit (ADK), mounts sibling Model Context Protocol (MCP) servers in-process, serves the studio wire contract over SSE, and provides session state management.

## Overview

The harness serves the studio (`docs/studio-contract-v1.md`). A turn is one orchestrator agent inside an ADK workflow. The agent decides what a question needs by calling tools, and code owns routing, the approval gate, retries and execution. When the agent hands a question to the plan path, the planner seam runs the planner-translator pair behind `harness.planner_seam`. The studio layer translates the workflow's run into the frozen wire contract the frontend builds against.

## The studio surface

Four conversation routes under `/api/studio` (see the contract doc for the full protocol), and the refresh route described under "The refresh route" below:

- `POST /api/studio/turn`: runs one turn, streams contract frames as SSE. A `component_ref` with `intent: "edit"` takes the Edit Card route instead (no search, no plan; see below).
- `POST /api/studio/interrupt`: resumes a paused turn (plan approval, elicitation answer/skip) on a NEW stream.
- `POST /api/studio/composition`: canvas mutations (add / reorder / remove / pin / unpin / set_layout_hints / set_card_meta), applied transactionally.
- `POST /api/studio/cancel`: aborts the conversation's in-flight segment (the Stop button).

Every request carries `Authorization: Bearer <token>` (`harness.auth`: presence required, optional shared secret via `STUDIO_API_TOKEN`) and a client-minted `conversation_id`. Each turn runs in a fresh per-turn ADK session (Edit Card turns bypass ADK entirely); the composition manifest, a canvas digest, and per-turn conversation records persist across turns in a per-conversation ADK "ledger" session, through the same ADK session service the runner itself uses (`harness.studio_state.StudioStore`); state is scoped to the (principal, conversation) pair. Any harness instance can load and continue a conversation another instance started, provided that session service is durable (`DATABASE_URL` or `SESSION_STORE_*` set); left unset, sessions live only in the process that created them and are lost on restart. A conversation streams at most one segment at a time, across every instance: a durable segment lease in the ledger (`studio:segment`, 45 s expiry, renewed every 5 s by its owner) backs the `/turn` and `/interrupt` claims, and a claim against a live segment answers the existing 409 `TRANSIENT_UNAVAILABLE` with `retry_after_seconds` set to the lease's remaining time; `/cancel` reaches a segment on any instance the same way, and the owning instance's heartbeat stops the stream within one heartbeat interval. The owning instance checkpoints the conversation's full state into the ledger before any frame that tells the client "paused" or "done" goes out; a checkpoint that fails ends the stream with a stream-fatal error in that frame's place instead. An `/interrupt` answer stays durable and retryable across a crash: the answer is saved before the resume starts, a retry of the same answer after the dead segment's lease expires resumes the turn again (its `seq` jumping 1000 past whatever the dead stream already sent), and a retry with a different answer is refused with `edit_conflict`. `/composition` can land on a different instance than the one streaming a turn; both sides reconcile through the ledger, so a concurrent canvas edit and the turn's own composition changes both survive. What a stalled owner still writes after losing its segment stays unfenced: its per-turn ADK session writes race the new owner's (ADK's own compare-and-swap fails one of the two), and a presentation-platform write already in flight can land as an orphaned component. Editing a card works from any instance. The component id grants reads, and the write token the platform returned on the card's create, held in the conversation's ledger state (`ConversationState.write_tokens`), grants revises; a card the conversation holds no token for is recreated in its slot instead.

## The refresh route

`POST /api/studio/refresh` (`harness.live_refresh`) redraws one card of a live share on current data. The website calls it server to server for a card drawn on a derived (`ops_`) frame. It takes `Authorization: Bearer <LIVE_REFRESH_PRINCIPAL>` and nothing else. `STUDIO_API_TOKEN` does not open it, the live-refresh principal opens no other route, and with the setting unset every call answers 401. It uses no conversation, model, or session.

The body is `{"component_id": "cmp_...", "revision": N}`. The route reads the revision's stored intent and its frame's recipe from dfo-apis, asks dfo-apis' frame refresh about each root dataset, and answers 200 with one of:

- `{"status": "current"}`: no root has moved, so the stored card stands.
- `{"status": "pending", "retry_after_s": N}`: a root is rebuilding, the replay has not finished, or the route is over its rate, in-flight cap, or row budget. Call again after the wait; finished steps are in the materialisation store and are skipped.
- `{"status": "redrawn", "render": {...}}`: `render` is dfo-apis' answer to rendering the revision on the replayed frame, untouched. The frame is found under the recipe's replay key when dfo-apis already holds it, and otherwise computed by `harness.recipe_replay.replay_recipe` and published with its recipe.

A refusal is `{"code", "detail"}`. `harness.live_refresh.REFRESH_CODES` lists the route's own codes:

| Code                     | Status | Retry can succeed | When                                                                                                    |
| ------------------------ | ------ | ----------------- | ------------------------------------------------------------------------------------------------------- |
| `unauthorized`           | 401    | no                | the bearer is missing or is not `LIVE_REFRESH_PRINCIPAL`, or that setting is unset                      |
| `request_invalid`        | 422    | no                | the body is not `{component_id, revision}` with a `cmp_` id and a revision of 1 or more                 |
| `component_not_found`    | 422    | no                | dfo-apis holds no such component, or no such revision of it                                             |
| `frame_unsupported`      | 422    | no                | the stored intent names no frame, or one that is neither `spec_` nor `ops_`                             |
| `dataset_frame`          | 422    | no                | the card is drawn on a dataset (`spec_`) frame, which dfo-apis refreshes itself                         |
| `recipe_missing`         | 422    | no                | dfo-apis holds no recipe for the card's frame                                                           |
| `recipe_invalid`         | 422    | no                | the stored recipe has no normal form hash, or a root that is no mint record                             |
| `dfo_apis_refused`       | 422    | no                | dfo-apis refused for good with a body that names no code                                                |
| `upstream_unavailable`   | 503    | yes               | dfo-apis did not answer, answered 5xx, or marked its refusal retryable; or a tool call did not complete |
| `refresh_not_configured` | 503    | no                | `DATASETS_FIRST_PARTY_PRINCIPAL` is unset, so recipes cannot be read                                    |

Any other code arrives under 422 and is permanent. It is passed through unchanged from the service that refused: a dfo-apis refusal that is not retryable (`render_target_mismatch`, `binding_invalid`, `rendering_not_recorded`, `refresh_not_permitted`), or a replay refusal (`recipe_normal_form_changed`, `root_rendering_ambiguous`, a verb's own code such as `growth_gap_year`).

A refresh has `live_refresh_deadline_s` (45 s) before its replay starts no new mint, verb, or publish, and the run is cancelled 8 s later with a `pending` answer, so no request runs past 53 s. Requests for one `(component_id, revision)` share one run in a process. Two instances replaying one card mint the same frame ids, and the second publish changes nothing.

## The workflow

`harness.graph.workflow.create_root_workflow` builds the workflow a turn runs: `seed` → `orchestrate` → `route`. `route` takes the one action the agent asked for: `ask` pauses for the user's answer and hands it back to `orchestrate`, and `plan_start` hands a brief to `planner` → `approve` → `execute`, whose result `plan_done` hands back to `orchestrate`. A turn whose agent asked for nothing ends at `route` with the agent's answer.

`seed` hands the agent the datasets the user brought from Search (`TurnRequest.seed_spec`). It resolves each seed's identity again through data-mcp (`harness.seeds.resolve_seed`), so the turn reads Search's current answer, and stores the seeds it keeps as definite parts of one search (`harness.graph.state.store_search`). The agent reads the kept parts as `search` returns them, with the operations the user asked of each, and each seed left out with why (`harness.seeds.seeds_hand_back`). It can then fetch or plan with a seed's spec_id without a `search` call, and later turns' ledgers show the seed as a reading. A seed data-mcp could not be reached for fails its own step `service_unavailable`, and one that Search does not resolve to the dataset the user brought fails `seed_dropped`. The turn goes on from the other seeds, or from the question when none is kept.

`orchestrate` runs `orchestrator.agent`'s agent, which decides what a question needs by calling tools (`harness.orchestrator_tools`): `search` sends the question and every part it names to data-mcp in one call and returns each part's reading; `fetch` retrieves one dataset (a family of indicators summed by the compiler's own rule) and describes its frames, and a retrieval with no observations comes back as an `empty_result` refusal, kept for the turn, with no frame registered; `make_charts` draws as many charts as help, through the workflow's binding check (`harness.chart_binding.select_binding_ok`) and the same recording executor; `get_skill` loads a skill a search result named and `get_skill_file` reads a file it links or the next page of a long one; `explain_dfo` answers a question about DFO itself from the `dfo-faq` skill (`harness.dfo_faq`); `recall` returns an earlier turn's plan records, readings or a canvas component in full when the digests' one-line summaries are not enough. Greetings and the like get a reply with no tool call. Each tool's calls per turn are capped, and the download surface fetches one dataset and plans nothing.

Every calculation the agent asks for goes through `plan`, and every plan shows the user a card. `ask_user` and `plan` record one pending action, and `route` acts on it once the agent's turn ends: `ask` pauses with the clarify interrupt, its options as candidates under generated ids, and hands the user's answer back to the agent in the option's words; `plan` hands the brief to the `planner`, `approve` and `execute` nodes, with the asks the call lists (each output the user asked for, at least one) under `planner.plan.ASKS_STATE_KEY`. The plan card shows each ask with the steps that answer it or why it is declined, and `plan_done` hands the executed plan's final-step frames back under ids the agent can chart, with each ask's outputs and whether each ran with data. A plan that cannot be made or run hands its reason back (`harness.wiring.handing_back_planner_failures`) with the plan's steps and their spec ids, gives the plan call back once, and the agent retrieves what it still can. A skipped question closes the turn with an offer to help with something else.

The agent streams: thought summaries as a running `activity.step` labelled with the thought's latest heading, each tool call as a running step labelled from its arguments, answer text as `message.delta` chunks. The plan path's status lines, step progress and pauses come from the workflow's nodes.

Everything external is injected: `harness.mcp_client.McpResolver` and `McpExecutor` call the loopback MCP mounts (presentation clients are held per conversation and send that conversation's caller), and `definition_surface` reaches the data-mcp `seed` resolves seeds through. The seams are async, since a sync seam would deadlock the loopback mounts.

The planner seam is `harness.planner_seam.PlannerSeam`, which `harness.wiring.build_planner` builds over `harness.agents.create_planner_with_translator`. The planner drafts a plan, has it translated and compiled by the translation each accepted `propose_plan` runs, and calls its own tools along the way, so one plan costs several sequential model calls. The seam puts the conversation's search readings in the opening user message, so a fresh plan grounds in what search already found. What a plan may name is fixed downstream of the planner: translation builds typed operations and the compiler's capability table maps each to a tool, checked against the live MCP schemas. The workflow's own state is the plan's authoritative record; the seam's session is authoritative only for drafting. Whenever the workflow hands the seam a prior plan, the seam seeds it into its own ADK session before the turn runs, and the `planner` node validates the `planner.plan.Plan` the seam returns. An amendment arrives as a real next user turn: the seam reuses the planner's session, so the planner's own amend path runs.

The planner reads skills through data-mcp's `get_skill` and `get_skill_file`, wrapped as its own function tools over the same tool surface the translation uses (`planner.skills`). When data-mcp has no Skills API, both tools refuse `capability_unavailable` and the planner drafts without skills.

## The Edit Card route

`component_ref.intent: "edit"` bypasses the workflow: describe the component, one constrained model call decides between a revise PATCH (title/select, the fields the hosted platform accepts in a revision) and a full RECREATE (type/window changes → new component, block replaced in place), then the platform write streams back as `component.revised` or `component.created`.

## Context discipline

Models see digests, and rows stay in the materialisation store. The agent reads part readings, frame views, one-line summaries, and of a drawn card what it holds and the figures a reply may state (`harness.reply_figures`), and the executor returns frame references. Cross-turn context is two digests every agent request opens with (`orchestrator.agent.prepend_digests`): the canvas digest (block titles and fact summaries, newest 16 blocks) and the conversation digest (newest 10 turn records, byte-capped). The agent's `recall` tool serves what lies past either bound, answered by the store (`harness.studio_state.make_recall_part`) with turn records, readings or a card's entry.

## In-process MCP server mounting

`harness.server.create_app` mounts the `data-mcp`, `analysis-mcp`, and `presentation-mcp` FastMCP applications as ASGI sub-apps under `/mcp/data`, `/mcp/analysis`, and `/mcp/presentation`.

Mounting sub-apps in-process lets all services run within a single Cloud Run instance over loopback HTTP.

```python
from fastmcp.utilities.lifespan import combine_lifespans

app = FastAPI(
    title="harness",
    lifespan=combine_lifespans(
        data_mcp_app.lifespan,
        analysis_mcp_app.lifespan,
        presentation_mcp_app.lifespan,
        _lifespan,
    ),
)
```

Each mounted FastMCP application relies on an internal `StreamableHTTPSessionManager` initialised during its lifespan. `combine_lifespans` runs the harness lifespan alongside every mounted sub-app lifespan so all session managers start cleanly. The harness lifespan runs last so its own startup self-check (below) finds every mount already up.

Each mount requires a bearer token (`FastMCP(auth=...)`, `common.auth`). `create_app` calls `common.auth.apply_gate` on all three before building their ASGI apps. Because fastmcp's auth wrapper covers only the streamable-HTTP MCP route, `custom_route` health probes like `/mcp/data/healthz` are unaffected. A 401 from a mount is an HTTP-layer rejection rather than an MCP protocol error (`raise_on_error=False` on `call_tool` doesn't catch it), so `_lifespan` opens an in-process client against the data-mcp mount and calls `list_tools` before yielding. A misconfigured token then fails startup instead of a user's first turn.

The three direct mounts answer only loopback clients, apart from their `/healthz` routes and presentation-mcp's `/theme-<hash>.css`, which a view's iframe loads from the host's browser. The harness's own clients reach them at `http://127.0.0.1:{port}`, and any other client address gets 403 before the bearer check (`_loopback_only` in `harness.server`). On Cloud Run an outside request arrives from the front end's address, which is never loopback, and uvicorn trusts `X-Forwarded-For` only from the addresses in `FORWARDED_ALLOW_IPS` (127.0.0.1 by default). Outside MCP clients use the combined server at `/mcp/`.

Every MCP call the harness itself makes carries a caller in the `x-dfo-caller` header (`common.caller`, `compiler.caller_clients.caller_transport`): `conversation:<digest>` derived from the studio conversation id inside a turn, no header outside one. data-mcp and analysis-mcp record it as the writer of each frame they store (`common.caller.current_writer`). presentation-mcp does not read it: the component id grants reads, and the write token held in conversation state grants revises.

## The combined server

`harness.combined_mcp.build_combined_mcp` mounts data-mcp's, analysis-mcp's and presentation-mcp's `FastMCP` objects, unnamespaced, into one parent that `harness.server.create_app` serves at `/mcp/` alongside the three direct mounts. `mount()` runs a child's tool in process through the child's own middleware, with no second MCP session, so an outside client sees one server carrying every data, analysis and presentation tool and presentation-mcp's `ui://presentation-mcp/renderer-{version}.html` resource. The theme stylesheet a view's iframe loads stays on the presentation-mcp mount, at `/mcp/presentation/theme-<hash>.css`. `combined_http_app` builds it with `path="/"` (the MCP endpoint sits at the mount prefix itself; FastMCP's default path would stack a second `/mcp` under it) and `stateless_http=True` (any instance serves any request, no `Mcp-Session-Id` needed). A bare `/mcp` answers Starlette's 307 to `/mcp/`.

Middleware runs only for calls through the combined server, outermost first:

- `_ExternalCallBudget` runs the call under data-mcp's `EXTERNAL_CALL_BUDGET`, whose `get_data` deadline is 42 s, 3 s inside the call limit, so `get_data`'s own refusal (`operation_still_processing`, `mint_unanswered`) reaches the caller before `_CallLimit` stops the call (`data_mcp.deadline`).

- `_RequestLog` logs the tool name or resource URI, the outcome (`ok`, the refusal's `code`, or the raised exception's name), the protocol revision, the caller, the trace id, and four host fields: `client` and `client_version` from the client's `clientInfo`, `views` (`declared`, `undeclared` or `unknown`, from `presentation_mcp.server.view_support`, the reading presentation-mcp's tools answer by) and `view_mime_types`, the mime types the client listed under the `io.modelcontextprotocol/ui` extension. It logs each initialize request with the same host fields. A 2025-11-25 client declares itself on initialize alone, so its calls to the stateless `/mcp/` log `client=None` and `views=unknown`; a 2026-07-28 client sends its capabilities, and usually its client info, with every request. Client-supplied strings are cut to 128 characters and written as JSON strings, except a tool name of letters, digits, `_`, `.` and `-`, which is written bare so `tool=search` matches. A `ui://` URI is logged whole and any other URI as its scheme and host, without any userinfo, since a `dfo://artifact` URI is a bearer credential; a URI with no `://` logs as `""`. No line carries a header, a tool's arguments or its result. For example:

  ```text
  combined mcp initialize outcome=ok revision=2025-11-25 caller=ip:3f9a2c1b client="claude-ai" client_version="0.1.0" views=declared view_mime_types=["text/html;profile=mcp-app"]
  combined mcp call resource outcome=ok revision=2025-11-25 caller=ip:3f9a2c1b trace_id=4bf92f3577b34da6a3ce929d0e0e4736 client=None client_version=None views=unknown view_mime_types=None uri="ui://presentation-mcp/renderer-c7b950ab.html"
  ```

  It runs each tool call, resource read and `resources/list` in a span the telemetry backend records (`common.telemetry.use_request_span`): fastmcp's own SERVER span per request under plain OTel, a Langfuse observation in that trace under Langfuse, which exports only its own spans, and one random id when no tracer provider is set.

- `_InFlightLimit` refuses a tool call `rate_limited` at once, without queueing, while `combined_mcp_max_in_flight` (default 16, per instance) tool calls, resource reads, `resources/list` requests and Skills over MCP extension methods are already running. A resource read over the cap fails with `rate_limited: ` text, and a `resources/list` with JSON-RPC `-32603` and the same text, since FastMCP answers any other exception a listing raises with fixed text.

- `_ToolCallRateLimit` draws every tool call from one token bucket, sized by `combined_mcp_requests_per_s` and `combined_mcp_burst` (per instance, one bucket for every caller). A tool call over the limit refuses `rate_limited`. Initialize, `tools/list`, resource reads and pings do not draw on it.

- `_CallLimit` cancels a tool call or resource read still running at 45 s (`data_mcp.deadline.EXTERNAL_CALL_LIMIT_S`). A tool call refuses `service_unavailable` with `retry_after_delay`, naming the tool and the limit. A resource read fails with `service_unavailable: ` text. `search`, `describe`, `get_skill`, `get_skill_file` and the artifact resource have no deadline of their own beyond the upstream client's 120 s retry budget, so this limit is what bounds them for an outside caller. A `resources/list` reads the skill catalogue from the Skills API (`data_mcp.skills_resources`), on every listing, the same uncached read a Skills over MCP extension method makes, so it is cancelled at that method's 10 s (`_SKILLS_READ_LIMIT_S`) and fails with `-32603` and `service_unavailable: ` text. `resources/templates/list` reads nothing upstream and is not limited.

- `_ShapeResults` drops `structuredContent` from a successful result and `outputSchema` from `tools/list`, so a client sees only the digest text `content` carries. A tool whose `tools/list` entry declares `_meta.ui.resourceUri`, presentation-mcp's `write_component` and `describe_component`, is an MCP App tool, and its results pass whole: `structuredContent` carries the view's layout and `_meta` the values it binds. From every other tool, `_meta` passes without `search`'s envelope.

- `_RefuseRaisedErrors` turns a raised error into a refusal in the same envelope: `tool_not_found` for a name no tool carries, `request_invalid` for arguments that fail a tool's input schema, `internal_error` for anything else a tool raised. A resource read that raised an unexpected exception fails with fixed `internal_error: ` text; the artifact resource's own refusals pass through unchanged.

The in-flight cap and the token bucket sit outside the call limit, so a call they refuse is answered at once, and the in-flight cap sits outside the token bucket, so a call it refuses spends no token. An `internal_error` carries none of the exception's text, which can name a bucket or a service account. `common.refusal.log_unexpected_error` logs the exception with its traceback under the call's trace id, the same id `_RequestLog` logs, and the refusal carries fixed text with no id. analysis-mcp's backstop and presentation-mcp's safety net answer the same way.

Every refusal the parent writes itself, and every one data-mcp's and analysis-mcp's own `to_tool_result` write, carries its `code`, `retry_mode` and `fix` in `content` as one line of compact JSON after the message (`common.refusal.refusal_text`), so a client that shows its model only `content` still reads the whole envelope. data-mcp caps the dfo-apis mint slots an outside `get_data` call can hold, per process, with `EXTERNAL_MINT_CONCURRENCY` (`data_mcp.settings.Settings.external_mint_concurrency`, default 1); a call over the cap refuses `service_unavailable`.

## Refused cards

A `write_component` refusal reaches the agent through `make_charts` as the refusal's own `message`, with the platform's `fix` as `advice` when it names the values the platform would accept. `make_charts` refuses a chart before any write when `harness.chart_binding.select_binding_ok` finds a select the platform would refuse (`select_invalid`, `series_limit_exceeded`), and treats a write that answers `ok` without a usable component (`harness.wire.usable_component`) as refused. A select over the series cap is first narrowed: `make_charts` reads the frame from the materialisation store, under the pair the retrieval states the store holds it by (its `frame_ref`, kept as the registered frame's `store_ref`, which a `groupby` sum or extra columns make a pair of its own, apart from the pair dfo-apis serves the frame under), and lists the largest members of the one dimension that multiplies the series, highest first, by their value at one period: the one period the members the chart could show hold between them, or when they hold several, their frame-grammar anchor (`latest_anchor`), the newest period at least half of them hold, and only members holding a value there are listed (on a place or flow party dimension, only the members one ranking compares: the parties of kind `party`, or the places at the level most of them share, read from the frame's own rows when they carry the dimension's kind or type column, as a plan's retrieval asked with `place_types` or `without_party_totals` does, and otherwise from the same retrieval asked again with `place_types`, once per frame in a turn, and rows are ranked without those columns), as many as the chart draws (8 lines, 24 series, a table within 2,000 rows), ends the title with `(N largest of M in <period>)`, M counting the compared members that hold a value at the period, and asks the reply to say so. A cut bar chart whose period was chosen among several is written with a window that starts and ends at that period, so dfo-apis draws the period the cut ranked at; a cut line chart or table keeps its window. The ranking runs in a worker thread, and the frame's rows stay claimed on the row budget until it returns. A cut whose kind read fails is refused as `member_kind_unread`, and one whose members hold several periods with no anchor as `no_shared_period`. A table or line chart with `order_by_value` lists its compared members highest first under the cap too, those with no value at the period last. A frame whose period moves with the data, a plan's rank positions, rows that differ in unit, source, method or measure, and a frame the store cannot read are drawn as the select names them, or refused as before.

`McpExecutor` stamps every refusal it returns with an `origin`: `service` when an MCP service refused, `harness` when the harness minted the refusal. It mints three: `unknown_tool` (a tool it does not route), `resolved_revision_unavailable` (a card it withholds because the `write_component` result carries no resolved revision to draw) and `provenance_unavailable` (a card it withholds because no citable source could be tied to the frame). The Activity step detail shows `<code>: <message>`, cut to 400 characters.

## Health and telemetry state

`GET /healthz` returns `service`, `version` and `telemetry`, the backend `common.telemetry` resolved at startup (`langfuse`, `otel` or `off`). On Cloud Run the Google Frontend answers the exact path `/healthz` itself, so `GET /status/telemetry` returns `{"telemetry": ...}` from a path that reaches the app, and both routes are unauthenticated and report telemetry as the state alone.

## The planner and its translation

`create_planner_with_translator` in `harness.agents` builds the planner that carries the plan-approve-execute workflow. The planner (`planner`, a second top-level module in this service) settles methodology with the user and records each choice as a `Decision` and what evidence the answer rests on as `EvidenceRequirement`s. The translator (`translator`, a third, code rather than an agent) finds the data each requirement needs and builds the operations each requirement states; the compiler (`compiler`, a fourth) turns those into the workflow the user approves, checked against the plan and the live MCP schemas.

The translator reaches the planner through `propose_plan`, one of the planner's six function tools (`get_skill`, `get_skill_file` and the four plan tools `src/planner/README.md` lists). `translator.tool.build_translate(*, surface)` returns an async callable, which `harness.agents` passes to the planner, and every accepted `propose_plan` runs it on the plan it recorded. The plan travels through session state, under `planner.plan.PLAN_STATE_KEY`, and no model runs inside the call. A transient verdict is retried by proposing again.

An accepted `propose_plan` returns its own payload plus `translation`, a typed result rather than prose. `translation` is `{"outcome": "ok"}` once the plan compiles and moves to PENDING_APPROVAL, or the referral itself, carrying `kind`, `reason`, an `outcome` from the closed set (`choice_required`, `invalid_input`, `unsupported`, `transient`, `internal`), and whichever of `requirement_id`, `candidates`, `constraint`, `repair` and `reference` that kind names.

- `settings`: The service settings, read for the MCP URLs `build_tool_surface` covers.
- `agent_settings`: The planner's model, from `planner.settings.AgentSettings`. Defaults to reading the environment.
- `surface`: The tool surface the translation discovers on and the compiler checks against, and the one the planner's skill tools call through. Tests pin one so the planner builds with no reachable MCP server.

Nothing computes or retrieves until the user approves. A `propose_plan` whose translation compiles declares the plan ready for the user's answer in code (`planner.agent.declare_ready`), approving nothing and asking nothing of the user itself, and returns the revision that answer is checked against. The gate that withholds execution is the workflow's `approve` node, downstream of the planner (`harness.graph`, `harness.planner_seam.PlannerSeam`). `PENDING_APPROVAL` is translation's status to write and no other planner tool can produce it. `harness.wiring.build_planner` builds the planner seam the workflow runs. See `src/planner/README.md`, `src/translator/README.md` and `src/compiler/README.md`.

## Structured content and the model boundary

An MCP tool's response splits `content` (the digest the tool renders for a model) from the envelope for calling code, which `structuredContent` carries for most tools and `_meta` carries for a `search` success, whose `structuredContent` is a small answer a host may show a model. Every model call site reads an envelope in code and consumes it there, leaving only the rendered digest for a model to see:

- `harness.mcp_client.McpResolver` and `McpExecutor` read a result's `structuredContent` (a `search` success carries a small model-facing answer there, so `McpResolver` reads its envelope from `_meta[SEARCH_ENVELOPE_META_KEY]`, `data_mcp.search_result`) to decide an outcome and return the workflow's own `frame_refs` and one-line `summary`, or a typed `refusal`. The digest text rides along only as a fallback `message` on an arg-validation error that carries no structured body.
- `translator.discovery.discover_source` reads a `search` envelope from the result's `_meta` (`ToolCallResult.meta`) through `compiler.sources.outcome_from_envelope` and answers with `compact_source`'s own field set. `fetch_definitions` keeps one `definition` string per source out of a `describe` answer.
- `harness.mcp_client.McpExecutor._get_data` stores the mint manifest in the provenance store and answers with `_manifest_summary`'s one line, read off the manifest, not the digest. `executor.run` keeps each server's digest text as its step's `StepRecord.digest`, and `plan_done` hands those to the agent as `step_summaries`. `harness.studio_translate._surface_call_outcome` gives a successful tool-surface `get_data` call the same `_manifest_summary` line for the Activity feed, and any other call none.

The planner's model reaches these Python functions through `FunctionTool`s (`harness.agents.create_planner_with_translator`). ADK's `McpTool` plays no part, so no `CallToolResult` dump is built on the served path. The `after_tool_callback` registered there (`harness.planner_seam.PlannerSeam`) counts events and sets tracker flags. Every envelope is consumed before a model call, so stripping `structuredContent` is unnecessary.

## Session service

`harness.session_store.build_session_service` chooses the ADK session backend from `Settings`, in this order:

- Both `database_url` and `session_store_instance_connection_name` unset: an `InMemorySessionService`. Sessions live only in this process and are lost on restart. The right default for local dev.
- `database_url` set: ADK's `DatabaseSessionService` over that plain SQLAlchemy URL (local Postgres or sqlite).
- `session_store_instance_connection_name` set: `DatabaseSessionService` over an async engine built on the Cloud SQL Python Connector (PSC, IAM auth), the deployed `ai` Cloud Run instance's path to the platform Postgres instance. `session_store_database` and `session_store_runtime_db_user` are required alongside it. `session_store_pool_size` and `session_store_max_overflow` size that engine's connection pool; `session_store_connect_timeout_s` bounds one connector dial attempt.

Setting both `database_url` and `session_store_instance_connection_name` is a construction-time error. This same session service backs both the runner's per-turn ADK sessions and the studio layer's per-conversation ledger session (`harness.studio_state.StudioStore`), so a durable backend here lets both a conversation's wire state and its plan-drafting state survive a restart or move to another instance. `harness.server.create_app` builds the service eagerly and disposes it (`SessionServiceHandle.aclose`) from the harness lifespan's shutdown phase.

The connector-backed engine opens 2 pooled connections per instance and no overflow (`session_store_pool_size`, `session_store_max_overflow`); a rollout can leave an old revision still draining SSE streams running alongside the new one, so up to four instances hold connections at once, and four times two stays within the ten connections dfo-infra's platform Postgres instance reserves for it. The harness lifespan calls `DatabaseSessionService.prepare_tables` at startup and retries it with exponential backoff for up to 120 s, inside Cloud Run's default 240 s startup probe window, before failing the probe, so a runtime identity's IAM grant still propagating does not kill a fresh revision.

google-adk 2.10.0 declares a new index on the `events` table, `idx_events_app_user_session_ts_id`. When the index is missing, `prepare_tables()` creates it at startup with a plain `CREATE INDEX`, which blocks writes to `events` until the build finishes and counts against the 120 s startup budget. A small table builds in well under a second and needs no manual step. Before deploying to a database whose `events` table is large enough for the build to approach that budget, create the index out of band as the table's owner, outside a transaction:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_events_app_user_session_ts_id
  ON events (app_name, user_id, session_id, timestamp DESC, id DESC);
```

`prepare_tables()` then finds the index and creates nothing. ADK leaves the index it replaces, `idx_events_app_user_session_ts`, in place. Drop it with `DROP INDEX CONCURRENTLY` once no revision running google-adk 2.9 is serving.

## Settings

`Settings` in `harness.settings` extends `BaseServiceSettings` from `common`.

- `port`: Port integer for the HTTP server, defaulting to 8080.
- `model_name`: Gemini model id used by every model call, pinned to a specific version so behaviour changes only when the pin does. `.env.example` ships the default.
- `data_mcp_url`: URL for the data MCP service. Defaults to `http://127.0.0.1:{port}/mcp/data/mcp`.
- `analysis_mcp_url`: URL for the analysis MCP service. Defaults to `http://127.0.0.1:{port}/mcp/analysis/mcp`.
- `presentation_mcp_url`: URL for the presentation MCP service. Defaults to `http://127.0.0.1:{port}/mcp/presentation/mcp`.
- `PRESENTATION_PUBLIC_URL` (read by the mounted presentation-mcp's `Settings`, not by the harness's): the URL at which a browser reaches presentation-mcp, `<public https URL>/mcp/presentation`. It is required and has no default. The harness fails at import when it is unset or not a valid absolute `http(s)` URL. Views load their theme stylesheet from it. `just dev` and `just studio-live` set it from `PORT`.
- `database_url`: Optional SQLAlchemy URL for a durable session store (local Postgres or sqlite). Mutually exclusive with `session_store_instance_connection_name`.
- `session_store_instance_connection_name`, `session_store_database`, `session_store_runtime_db_user`: Together select the Cloud SQL Connector session-store path over `database_url`'s plain-URL path; required together, and refused together with `database_url`.
- `session_store_pool_size`, `session_store_max_overflow`: Pooled connections the connector-backed engine opens (defaults 2 and 0, two per instance).
- `session_store_connect_timeout_s`: Bounds one Cloud SQL Connector dial attempt, in seconds (default 30).
- `studio_api_token`: Shared secret for the studio routes; when set, studio requests must present exactly this bearer token (`harness.auth`). **Placeholder access control:** unset, any non-empty bearer token is accepted and the live server logs `STUDIO AUTH IS OPEN` at startup. Set it on every server reachable beyond the developer's machine.
- `orchestrator_thinking_level`: Reasoning effort of the orchestrator agent: `LOW`, `MEDIUM` or `HIGH`, case-insensitive. Unset or blank means `LOW`, the default; any other value fails at startup. Override with `ORCHESTRATOR_THINKING_LEVEL`. Thought summaries are requested at every setting and reach the traces only.
- `studio_cors_origins`: Comma-separated browser origins a live server answers CORS preflights for, e.g. `http://localhost:8091` for a locally served page testing against the real agent. Empty (the default, and the deployed posture) sends no CORS headers; the deployed service is reached same-origin through the website's proxy.
- `mcp_api_token` (inherited from `BaseServiceSettings`): Shared bearer token the three MCP mounts require (`common.auth`). Unset (the default) mints one at startup and hands it to the harness's own MCP clients, so a local run needs no configuration. Set it before pointing `DATA_MCP_URL` / `ANALYSIS_MCP_URL` / `PRESENTATION_MCP_URL` off loopback. Construction refuses that combination without it, and refuses an off-loopback URL over anything but `https` even with it set, since that bearer is attached to every request.
- `mcp_auth_disabled` (inherited from `BaseServiceSettings`): Turns the MCP mount gate off entirely, for a raw client with no bearer token to present. Logged at error level. Never set on a server reachable beyond the developer's machine.
- `combined_mcp_requests_per_s`, `combined_mcp_burst`: Size the combined server's one token bucket per instance (defaults 5.0 and 20), refilled at `combined_mcp_requests_per_s` and holding at most `combined_mcp_burst`. Every outside tool call to `/mcp/` draws on it, and no other request does. There is one bucket for every caller.
- `live_refresh_principal`: The bearer `POST /api/studio/refresh` takes, and the principal the harness presents to dfo-apis' frame refresh and render routes (`LIVE_REFRESH_PRINCIPAL`). Unset or blank, the route refuses every caller with 401 and startup logs `LIVE REFRESH IS CLOSED`. Startup fails when it equals `studio_api_token`.
- `live_refresh_deadline_s`: Seconds one refresh has before its replay starts no new step (default 45, at least 30, the least that leaves a root mint its 25 s). The run is cut 8 s after it.
- `live_refresh_requests_per_s`, `live_refresh_burst`, `live_refresh_max_in_flight`: The refresh route's own token bucket (defaults 2.0 and 20) and in-flight cap (default 8), per instance and apart from the combined server's. A request over either answers `pending`. The burst is one live canvas of 20 cards opening at once. The cap is half the combined server's 16, since a replaying refresh holds its slot for up to 53 s.
- `live_refresh_rows_in_flight_max`: Size of the row budget replays claim from (default 500,000, one two-input verb on two full frames, and at least twice `MAX_FRAME_ROWS`). It caps the input rows of the verb calls, anchor calls, and publishes all replays in the process run at once. The tools and the publish claim the same rows from the process-wide `FRAME_ROWS_IN_FLIGHT_MAX` budget as well, and a root mint claims there only, so this setting keeps replays from filling the shared budget and leaves their rows counted in it. A claim that fits neither answers `pending`.
- `turn_model_time_s`, `turn_model_calls_max`, `turn_wall_s`, `model_first_chunk_s`: One request's bounds on its model calls (`harness.turn_budget`), a request being one POST to `/api/studio/turn` or `/api/studio/interrupt`. `turn_model_time_s` (default 90) meters the seconds the orchestrator's and the planner's model calls spend waiting on their streams, from each request sent to each chunk, genai's HTTP retries included, and leaves out tool time. It cuts a call still streaming. `turn_model_calls_max` (default 30) caps the model calls. `turn_wall_s` (default 600, under Cloud Run's 900 s) meters wall-clock time from the request's start, tool time included, and cuts only model calls and the discovery calls inside a planner entry. Other tool calls keep their own timeouts. `model_first_chunk_s` (default 12) resends a streamed call that has sent no chunk by then, once per request. A spent bound ends the request with its sentence from `harness.sentences` as the final message, with no further model call, unless it closes a planner call while the last referral names sources to choose from: the user is then asked to pick one. The Edit Card's model call takes `turn_model_time_s` as its HTTP timeout. `harness.graph.state.BUDGETS` counts tool calls apart from these.

Setting explicit environment variables for `DATA_MCP_URL`, `ANALYSIS_MCP_URL`, or `PRESENTATION_MCP_URL` redirects agent tool calls to external endpoints.

`model_name` drives the orchestrator agent and the Edit Card's model call (`harness.generative.GeminiEdit`). The planner reads its own model from `AgentSettings` in `planner.settings`, which this service and the eval agents share.

- `planner_model_name`: Model the planner runs, pinned to `gemini-3.8-flash`. Override with `PLANNER_MODEL_NAME`. It pins a concrete version rather than a floating alias, so an eval score stays attributable to one model.
